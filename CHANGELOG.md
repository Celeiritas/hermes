# Changelog

## 0.2.0 – 2026-10-20
- **Both ways.** `hermes send <route> <files…>` on the server stages a hardlink of each file (a copy across drives; the original is never touched) with `direction: out`, lets the same door and the same Janus check run, then sends it by Taildrop (`tailscale file cp`) as `<prefix><name>`, e.g. `hermes__report.pdf`. Hermes removes its own staging link once Tailscale confirms. A device that is asleep makes the item wait in `<stage>/outbox/<id>/` (logged `waiting` once); `hermes collect` tries again on every run for the route's `retry_hours` (24 by default), then it is `undelivered` with an alert. `hermes release` and `hermes discard` work on outbound items too
- **Phone Taildrops.** `hermes collect` (`units/hermes-taildrop.timer` every 2 minutes, `.service` a one-shot, and "Collect now") retries the outbox, then runs `tailscale file get --conflict=rename` **without** `--wait` into `<home stage>/incoming/taildrop/` and hands every file to the door with `sender.via = "taildrop"`, the route from `taildrop.by_kind` by file ending, else `taildrop.default`; a kind with no route is set aside in `failed/`. A run with nothing waiting writes nothing and takes well under 0.5 s with the fake (the number on the server is still owed)
- **Messages.** `hermes message <route>` reads up to 4 KB of text on stdin: a magnet link becomes `<hash8>.magnet` (the info-hash's first 8 characters), a URL `link-<time>.txt`, anything else `note-<time>.txt` (so `hermes__note-….txt` on the PC); `meta.json` carries `message.type`. Messages go through the door like files; `--user` records who sent one when the Delivery page knows
- The door: an arrival's `direction` must match its route (in → a folder, out → a device), one door per stage at a time (a lock file, so `hermes send`, `hermes collect` and the path unit never race), `outbox/` and `undelivered/` among the folders; `hermes status` lists both and the alert covers undelivered items
- `clients/dolphin/hermes-send-to-pc.desktop`: "Hermes: send to {{PC}}" in Dolphin's right-click menu → `hermes send pcmail`. `scripts/retire-taildrop-collector.sh [--go]` finds whatever collected Taildrops before Hermes (user units, timers, crontab lines running `tailscale file get` or writing to Hermes-Mail) and sets it aside with a dated name; preview first, never deletes
- `docs/both-ways.md` (how each direction works, the `tailscale file get` no-wait check to record on the server, the quiet-run timing), `docs/files.md` updated. The fake `tailscale` now answers `file cp`, `file get` and `version`
- Tests: send (through the door, a hardlink, the original untouched even when quarantined, refusals, a copy across drives), the outbox (offline → waiting → retried → sent; offline for longer than `retry_hours` → undelivered + alert; release of an outbound quarantine), Taildrops by kind (a `.torrent` to the watch folder, a photo to the mail folder, an `.exe` quarantined, no route → `failed/`), a quiet collect that is fast and writes nothing, no tailscale, messages (magnet, note, link, refusals), direction checks, the door lock, the command line, the units, the menu and the retire script

## 0.1.4 – 2026-10-20
- **The door's delivering side.** `hermes door` (started by `units/hermes-door.path` → `hermes-door.service`, a one-shot) takes every arrival in every stage's `in/`, asks `janus check --json` with a timeout that grows with the file, and acts on the verdict: **pass** → the route's `to` (one rename; copy + fsync + rename + remove the staged copy only across drives), the route's `conflict` rule (`rename` → `name (2)`, `skip` → `skipped/`, `replace` → the older copy to `replaced/`), exec bits off, the folder's SELinux label when SELinux is on, the route's doorbell (`jellyfin-refresh`, from a fixed list); the arrival's `meta.json` and `verdict.json` go to `delivered/`. **quarantine** → `quarantine/<id>/` (data mode 0400). **duplicate** → `skipped/`. Janus missing, failed, timed out, or an answer that doesn't match its exit code → **held**, retried on every run and by `hermes retry <id>`; nothing is ever delivered without a pass. Every arrival leaves `in/`. The verdict is saved into the arrival before anything moves, so a run interrupted halfway is finished by the next one without asking Janus again, doubling a file or doubling a log line. The door is the boundary: every name (and subpath) is checked again with `receive`'s rules and must resolve inside the route's `to`; a bad one is quarantined with a verdict Hermes writes itself
- **Records**: one JSON line per outcome in `~/.local/share/hermes/log/deliveries-YYYY-MM.jsonl`; `hermes log [--json] [-n N]`; `hermes status [--json]` with today's counts, everything waiting in `quarantine/`, `held/`, `failed/` and `skipped/`, and the alert; the Argus alert file `~/.local/state/argus-ui/alerts/hermes.json` while quarantined or held items are unseen; `hermes ack` clears it
- **`hermes release <id> --reason <word>`** delivers a quarantined (or held) arrival anyway and logs who did it (ssh user, `tailscale whois`); **`hermes discard <id>`** moves a set-aside arrival to `~/.local/share/hermes/.set-aside-<date>-<time>/`. Nothing is ever deleted: only renames into `quarantine/`, `held/`, `skipped/`, `replaced/`, `failed/`, `delivered/` or the dated set-aside
- `docs/janus-contract.md` (what Hermes asks and what it does with each answer) and `docs/files.md` (meta, verdict, log, status and alert formats, the stage folders)
- Tests with the fake Janus: pass, quarantine, duplicate, error, timeout, missing, a non-matching answer; each conflict mode; interrupted runs (after the verdict, after the data moved, after a replace set the old copy aside); names and subpaths re-checked at the door; unknown and outbound routes; junk in `in/`; the door's own failures; across drives; SELinux; doorbells; release, discard, ack, status, log and the command line; a mixed run that deletes nothing

## 0.1.3 – 2026-10-20
- **`hermes receive` hardened** (review of the receiving side, #17). Names are NFC-normalized, and refused when they hold a control (C0 or C1), format (bidi overrides such as U+202E, zero-width U+200B, soft hyphen), private-use, surrogate or line/paragraph separator character, or end with a space or a dot (Windows can't make those). `<bytes>` must be 1–15 plain ASCII digits: a Unicode digit used to crash `int()` with a traceback. A transfer that sends nothing for 120 s is given up and set aside (`select` on stdin, `$HERMES_IDLE_TIMEOUT` for tests), both mid-stream and while waiting for the sender to close. Any unexpected error shows the sender one line and exits 3; the traceback goes to `~/.local/share/hermes/log/receive-errors.log`, never to the client
- `docs/keys.md`: the shell check uses `ssh -o IdentitiesOnly=yes -i …`, otherwise ssh offers your normal key first and opens a real shell, which looks like the Hermes key failed
- Tests: each refused category, NFC, Unicode and signed sizes, the idle timeout mid-stream and at the end, a pipe that closes in time, an unexpected exception

## 0.1.2 – 2026-10-20
- **The door's receiving side.** `hermes receive --key <device>` is the ssh forced command a sending device's key runs. It accepts only `ping` (→ `hermes ok <version>`) and `put <route> <name-b64url> <bytes> <sha256>` with the file on stdin: the file streams into `<stage>/incoming/<id>/data` and is hashed on the way, stops when more bytes arrive than declared or when the drive would drop below a 5 GB margin, and is checked against the declared size and SHA-256. `meta.json` records route, name, bytes, sha256, the key's device and `node`/`user` from `tailscale whois --json` on the address in `SSH_CONNECTION` (a whois failure is recorded as `null`, never fatal). Only the complete folder is renamed into `<stage>/in/` in one step. A short stream, a long one, a wrong hash or a broken connection sets the attempt aside in `<stage>/failed/<id>/` with `error.txt`. Names: no `/`, `\`, NUL or control characters, no leading dot, 200 characters at most; files are mode 600, never with an exec bit; `receive` runs at nice 10. Exit 0 ok · 1 transfer failed · 2 refused · 3 the server's own problem
- **`hermes keys add|list|remove <device> [pubkey-file]`** edits only the lines tagged `hermes:<device>` in `~/.ssh/authorized_keys`: `restrict,from="<tailnet ranges>",command="~/.local/bin/hermes receive --key <device>" <type> <key> hermes:<device>`. Every change first saves `authorized_keys.set-aside-YYYYMMDD-HHMM`; other lines are never touched. A private key, a malformed key or a key already on a non-Hermes line is refused; adding a device again replaces its line (rotation); `list` shows device, type, fingerprint and whether the line is still what Hermes writes
- `docs/keys.md`: setup, and the manual checks that a Hermes key can't open a shell, run another command, forward ports or an agent, or get a pty
- Tests: good file, empty file, short and long streams, wrong hash, broken connection, bad routes (unknown, outbound, closed), `../`, absolute, dot, backslash, NUL and over-long names, unknown commands, no `SSH_ORIGINAL_COMMAND`, whois failures, the disk margin before and during a transfer, broken config; keys add/list/remove, backups, untouched lines, refusals, the command line. A fake `tailscale` joins the fake `janus` in `tests/fixtures/`
